# 项目定位与技术讲解

## 一句话介绍

面向工程代码演进的经验驱动 Agent 参考实现：把历史工程对话整理成可追溯案例，
通过混合检索辅助规划，并以真实执行、独立验证和失败恢复闭合流程。

## 项目讲解顺序（约三分钟）

1. **场景**：算法组件替换经常涉及接口、配置与回退，多数风险不是“代码能不能生成”，而是工程约束是否被保留。
2. **经验建模**：对话抽取成 EngineeringCase；task、constraint、solution 三类视图保留来源，支持复用。
3. **检索设计**：语义模型处理意图相似；BM25 匹配异常和字段名；RRF 通过名次融合，按 Case 控制重复。
4. **执行闭环**：仓库事实与 Skill 约束规划；独立验证失败后，把错误加入下一轮查询；次数耗尽恢复原始状态。
5. **实验证据**：20 个合成案例、30 条查询的四组消融，MRR 提升而 Recall 有下降，展示明确取舍。
6. **工程产物**：每轮 JSON、阶段事件、HTML 报告、36 项核心测试以及项目展示页。

## 可以用于简历的表述

根据实际参与范围选择表述：

> 扩展工程经验驱动的 RAG Planning 项目，构建 EngineeringCase 结构化经验流程，
> 实现 BGE-M3 与 BM25 的 RRF 混合检索及 Case 级上下文限额；
> 通过独立验证、错误再检索与检查点恢复完成代码修改闭环，并提供可追溯运行报告。

> 构建 20 个合成工程案例、30 条分级标注查询的检索消融实验。
> 在 BGE-M3 / RTX 4090 的该开发集上，融合去重方案 MRR@5 为 0.9667，
> Dense 基线为 0.9111；同时披露 Recall@5 从 0.9333 降至 0.9000 的取舍。

如写入简历，应保留“合成开发集”这一条件；不要替换成真实业务提升、训练成果或生产规模结论。

## 面试可以深入的八个问题

### 为什么不是直接拼接完整历史对话？

原始对话冗长、可能相互矛盾且掺杂临时信息。Schema 将任务、约束、问题、方案和来源显式化。
代价是抽取可能丢失信息，因此保留来源 ID 以供复核；目前没有量化抽取保真率。

### 为什么不用 Dense 分数直接加 BM25 分数？

两者量纲与数值分布不同。当前采用 `sum(1/(60+rank))` 的 RRF。
它无需分数校准，但会忽略原始分数差距，权重和候选预算仍需要验证。

### 为什么要区分 Case 与 Chunk？

检索行是 Chunk；可复用经验的主体是 Case。一个案例的三个视图可能挤占全部上下文。
限额增加跨案例覆盖，也可能舍弃同一案例的互补信息，故它是可配置策略。

### 能否证明 RAG 让 Agent 更成功？

目前不能。检索实验只验证相关性排序，离线闭环使用预设 Planner。
真正的成功率实验需要固定模型、任务集、预算、验证器，比较有无 RAG 并重复运行。

### 为什么错误要进入新的检索查询？

任务描述往往只有迁移目标，实际错误包含缺失字段、异常类型与失败阶段，
可引出其他历史故障经验。每轮保留 query.json，支持确认重试是否真的改变依据。

### 白名单是不是安全沙箱？

不是。它限制工具的直接编辑入口；生成的 Python 在验证阶段仍能执行。
需要系统级隔离时，可以替换 ProjectAdapter，使执行发生在受限容器中。

### 回滚如何判断成功？

检查点记录原始字节与文件原本是否存在，恢复后逐项核对。
失败应明确报告 rollback_failed；当前内存中的 checkpoint 并不支持进程崩溃后的自动续跑。
验证子进程的非白名单副作用，也不在这一恢复保证内。

### 为什么没有先加入多智能体、知识图谱或微调？

当前最重要的问题是能否复现、能否追溯和能否证明收益。
先建立检索和执行的比较依据，再根据失败分布决定是否需要更复杂的机制。
这些能力并未在本版本中实现。
